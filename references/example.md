# 推送示例库

> 本文件是 [SKILL.md](../SKILL.md) 的附属参考。**组装推送内容前**来这里找最接近的场景，照着骨架改；不需要一次性读完，也不用预加载。

## 怎么用

> **用户偏好优先于本文件的所有示例。** 如果用户说过自己的推送偏好（要不要 emoji、单条还是多条、标题格式、要不要表格、是否要分通道），按用户说的执行；本文件的示例只用来补他没提到的部分。这与 SKILL.md 文首的「优先级总则」是同一条规则。

1. **先判给谁** → 数据要进你的业务系统（落库 / 入库 / 触发下游）看**第 1 节**，那里是 JSON + 零 emoji；给人看的通知看第 2 节及以后。**这一步做错，后面全白做。**
2. **定位场景** → 在目录里找最接近的一节。
3. **套骨架** → 保留分区标题和 emoji 结构，只替换里面的具体数值。
4. **必查三件事**：head 是不是「结论 + 一个 emoji」（webhook 则是纯文本批次标识）；body 有没有分区或是不是合法 JSON；有没有给「下一步」。

不要整段照抄示例。示例里的域名、金额、耗时都是占位数据，照抄会推送假信息。

### 长度参考

| 平台 | 标题可见上限 | 正文可见上限 |
|---|---|---|
| iOS | ~25–50 字符 | ~150 字符 |
| Android | ~65 字符 | ~240 字符 |
| Web push | ~30–50 字符 | ~80–120 字符 |

`head` 字段本身允许 200 字符，但**超过 30 字符就会被截断**。做法：**标题自带结论和关键数值，正文展开**。反例「2026 年 10 月 3 日的每日签到任务已经顺利完成了哦」；正例「🎉 签到成功：积分 +10」。

### 通用骨架

```
head: <emoji> <结论>：<关键数值>
body: ## <分区标题>
      - <结果符/状态灯> **<标签>**：<值>
      ...
      ## 📌 下一步
      1. <动作>
```

三类注入需要根据严重程度切换 head 的 emoji：**正常 🎉 / 🟢，注意 ⚠️ / 🟡，阻断 💣 / 🔴**。

## 1. Webhook：结构化数据入库（机器读）

> **这一节排在最前面是有意为之：动手之前先分岔。** push-server 有两类完全不同的用法，走错分支等于白推——给机器的数据加了 emoji 会 `JSON.parse` 失败，给人看的 Markdown 塞进业务库会污染字段。

**两类用法**

| | **机器读（本节）** | **人读（第 2 节起）** |
|---|---|---|
| 通道 | webhook 类通道（`web_hook_push`） | 浏览器 / IM / 邮件等 |
| `body` | 一整段合法 JSON 字符串 | Markdown |
| emoji | **零个**（`head` 也不加） | head 一个 + body 按规范 |
| 终点 | 你的商品库、线索库、工单表、时序库 | 人的通知栏 |

**商业价值最高的一类用法就在这节**：不是「发个通知」，而是把 AI 的产出**变成业务系统里的一条数据**——AI 负责采集、清洗、结构化，push-server 负责把结构化结果原样 POST 到你自己的接收接口，落库、进仓、触发下游流程。人到人的通知只是它的副产品。

格式铁律：

| 项 | 规则 |
|---|---|
| `head` | 纯文本批次标识，如 `采集批次 2026-10-03T10:32`。它常被接收端当索引或去重键入库，加 emoji 等于毁掉唯一性 |
| `body` | **裸 JSON 字符串**：合法可 `JSON.parse`、不包 Markdown、不包代码块围栏、不含任何 emoji |
| 通道 | 必须是 webhook 类型通道码，别混用浏览器 / IM 通道 |
| 上限 | ≤50000 字符，超量拆批推或改推索引 |

**怎么判断走哪条**：看接收方是 `JSON.parse` 还是人的眼睛。用户没明说时，默认走人读版。

### 1.1 商品采集 → 商品库入库

```json
{
  "head": "采集批次 2026-10-03T10:32",
  "body": "{\"batchId\":\"20261003-1032\",\"source\":\"shop.example.com/new\",\"collectedAt\":\"2026-10-03T10:32+08:00\",\"total\":48,\"items\":[{\"sku\":\"SKU1001\",\"name\":\"降噪耳机\",\"price\":899,\"stock\":132},{\"sku\":\"SKU1002\",\"name\":\"机械键盘\",\"price\":459,\"stock\":3}]}"
}
```

要点：**字段名对齐你的表列名**；金额用数字类型不是字符串，否则入库后没法聚合；建议必带 `collectedAt` 和 `batchId`，否则无法增量、无法去重，重推一次数据翻倍。

### 1.2 线索名单采集 → CRM 入库

```json
{
  "head": "线索批次 2026-10-03 华东制造",
  "body": "{\"batchId\":\"lead-20261003-01\",\"region\":\"华东\",\"collectedAt\":\"2026-10-03T11:05+08:00\",\"leads\":[{\"name\":\"宁波xx精密机械\",\"contact\":\"王先生\",\"hash\":\"sha256:9f2c\",\"intent\":82},{\"name\":\"苏州xx自动化\",\"intent\":64}]}"
}
```

要点：联系人这类敏感字段**只推哈希或脱敏值**，不要出现明文手机号 / 邮箱（见 SKILL.md 安全红线）；每条数据建议要带唯一业务键（`batchId` 或 `sku` / 公司名），接收端才能幂等去重。

### 1.3 批量采集 → `send_multi_message` 分源入库

这是 `send_multi_message` **最正当的用法**：N 个采集源，每个源一条独立记录，各自入库各自的库表或走各自的 webhook 通道。

```json
{
  "channelCode": "11111111111111111111111111aaaaaa",
  "messages": [
    {
      "head": "采集批次 site-a 2026-10-03",
      "body": "{\"site\":\"site-a\",\"batchId\":\"20261003-a\",\"collectedAt\":\"2026-10-03T10:32+08:00\",\"ok\":true,\"total\":48,\"items\":[{\"sku\":\"A1\",\"price\":19.9}]}"
    },
    {
      "head": "采集批次 site-b 2026-10-03",
      "body": "{\"site\":\"site-b\",\"batchId\":\"20261003-b\",\"collectedAt\":\"2026-10-03T10:33+08:00\",\"ok\":true,\"total\":12,\"items\":[{\"sku\":\"B1\",\"price\":88}]}",
      "channelCode": "22222222222222222222222222bbbbbb"
    }
  ]
}
```

要点：**失败的源也要推结构化记录**，不能只推成功的——业务侧要靠它做任务对账和配额统计。

### 1.4 探测数据 → 监控 / 时序入库

```json
{
  "head": "uptime probe 2026-10-03T13:00",
  "body": "{\"target\":\"api.example.com\",\"checkedAt\":\"2026-10-03T13:00+08:00\",\"code\":200,\"rt\":312,\"healthy\":true,\"checks\":[{\"type\":\"http\",\"ok\":true},{\"type\":\"dns\",\"ok\":true}]}"
}
```

### 1.5 内容与舆情批次 → 内容库入库

```json
{
  "head": "舆情批次 2026-10-03 品牌词 24h",
  "body": "{\"keyword\":\"xx品牌\",\"window\":\"24h\",\"collectedAt\":\"2026-10-03T12:00+08:00\",\"items\":[{\"title\":\"xx品牌服务调整公告\",\"sentiment\":\"negative\",\"hot\":78},{\"title\":\"xx品牌发布新品\",\"sentiment\":\"positive\",\"hot\":52}]}"
}
```

### 1.6 五个高频踩坑

1. `body` 里包了 Markdown 代码块围栏（三个反引号 + json）→ 接收端 `JSON.parse` 直接失败。必须是裸字符串。
2. 数字写成字符串（`"price": "899"`）→ 入库后不能求和分档，除非对方列就是字符串。
3. 缺 `batchId` / `collectedAt` → 无法增量去重，重推一次数据翻倍。
4. emoji 或换行装饰混进 JSON 字段值 → 排序错位、唯一键失效，部分库直接报错。
5. 单条超过 50000 字符才拆批 → 超量前就该拆；大对象建议存对象存储，只推索引。

> 想看同一批数据**给人看**时的样子，见第 3 节（数据采集 / 网页变更监控）——同样一份采集结果，两条路的写法完全不同。

## 2. 网站签到 / 打卡 / 权益领取

国内自动化最高频的一类（签到脚本、网盘扩容、会员签到），每天都会推，所以**越短越好**——推长了三天就会被静音。

成功：

```json
{
  "head": "🎉 签到成功：积分 +10",
  "body": "## 🟢 签到结果\n- ✅ **站点**：example.com\n- ✅ **本次奖励**：+10 积分\n- 📊 **当前积分**：325\n- 🏆 **连续签到**：100 天\n- 🕐 **执行时间**：2026-10-03 09:14\n\n> 🎯 再坚持 5 天解锁「百日打卡」徽章"
}
```

重复签到（今天签过了，不算失败也别报成功）：

```json
{
  "head": "🟡 今日已签到，无需重复执行",
  "body": "- ⚪ **本次动作**：跳过（当日已签到）\n- 🏆 **连续签到**：99 天，纪录保持中\n- 📊 **当前积分**：315",
  "url": "https://example.com/user/sign"
}
```

失败（登录态失效是这个场景最主要的失败模式）：

```json
{
  "head": "💣 签到失败：登录态已失效",
  "body": "## ❌ 失败详情\n- ❌ **站点**：example.com\n- ❌ **失败原因**：Cookie 失效，请求被重定向到登录页\n- 🕐 **执行时间**：2026-10-03 09:14\n\n## 📌 需要你处理\n1. 🔑 更新站点登录凭据后我重新执行\n2. 🔍 确认是否触发了平台验证码风控\n\n> 🔒 凭据原文不会写入推送内容"
}
```

要点：**绝不在推送里出现 Cookie / Token / 密码原文**（见 SKILL.md 安全红线）。签到类消息通常每天推，成功后一句 `>` 引用就够了，别写成长报告。

## 3. 数据采集 / 网页变更监控

给你自己看（Markdown + emoji）；**要落库 / 进业务系统的话，改看第 1 节的 webhook JSON 写法**——同一批数据，两条路格式完全不同：

```json
{
  "head": "📥 商品列表采集完成：共 48 条",
  "body": "## 🟢 采集概览\n- ✅ 成功 **48** ｜ ❌ 失败 **2**\n- 🌐 shop.example.com/new ｜ 🕐 12.4s\n\n## 📋 预览（前 2 条）\n1. **无线降噪耳机** ｜ ¥899 ｜ 🟢 充足\n2. **机械键盘** ｜ ¥459 ｜ 🟡 仅剩 3 件\n\n> 📦 要入库？改走第 1 节的 JSON 写法",
  "url": "https://example.com/collect/2026-10-03"
}
```

网页变更监控（有变更才推，无变更不要推）：

```json
{
  "head": "👀 目标页面已更新",
  "body": "## 🔔 变更摘要\n- 🌐 **页面**：example.com/pricing\n- 📝 **区块**：价格表（企业版 ¥1,999 → ¥2,299）\n- 🕐 **检测于**：10-03 11:20（上次无变化）\n\n## 📌 下一步\n1. 🔗 查看 diff 快照",
  "url": "https://example.com/diff/9f2c"
}
```

要点：**head 带条数**，不用点开就知道规模；明细超过 5 条时只放预览 + 「… 其余 N 条同结构，略」。另外 Markdown 表格要慎用：接收端用 showdown 渲染 body，若未开启 tables 扩展，表格会被当成纯文本输出，这种情况改用「有序列表 + ｜ 分隔」更稳。

## 4. 服务器与站点监控

可用性巡检（正常）：

```json
{
  "head": "🟢 巡检通过：api.example.com",
  "body": "## 🟢 监控状态\n- 🟢 **状态码**：200 ｜ **响应**：312ms（阈值 1000ms）\n- 🟡 **证书剩余**：68 天，建议尽早续期\n- 🌐 api.example.com ｜ 🕐 10-03 13:00\n\n## 📊 近 24 小时\n- ✅ 可用率 99.8%\n- 🟡 12:07 出现 1 次 1.2s 慢响应"
}
```

探测失败：

```json
{
  "head": "🔴 探测告警：目标不可达",
  "body": "## ⚠️ 告警详情\n- 🏷️ **探测**：liveness（HTTP GET /）\n- 🔴 **等级**：服务不可用\n- 🔴 **失败项**：连接超时 >5s，连续 3 次\n- 🟢 DNS 解析正常\n\n## 📌 处置建议\n1. 🔍 检查安全组 / 防火墙\n2. 🧪 curl -I https://api.example.com 复现\n3. 📣 10 分钟未恢复则升级",
  "url": "https://grafana.example.com/d/uptime"
}
```

证书 / 域名到期（分级推送，越临近越频繁）：

```json
{
  "head": "⚠️ 证书将在 7 天后过期",
  "body": "## 🟡 到期提醒\n- 🌐 **域名**：www.example.com:443\n- 🔴 **剩余**：7 天（10-10 到期，阈值 30 天）\n- 🛠️ **签发方**：Let's Encrypt\n\n## 📌 下一步\n1. ♻️ 执行 certbot renew 续期",
  "url": "https://example.com/monitor/certs"
}
```

服务恢复（告警闭环的一部分，别漏）：

```json
{
  "head": "🎉 服务已恢复",
  "body": "- 🟢 api.example.com 已于 13:11 恢复，响应 420ms\n- ⏱️ **中断时长**：9 分 12 秒\n- 📉 **可用率影响**：本次事件 -0.6%\n\n> ♻️ 建议复盘超时根因，避免再次触发"
}
```

要点：**巡检类消息把状态灯直接放进 head**（🟢 / 🔴），因为「正不正常」就是唯一关键信息，比用 🤖 更快传达。只有**正常态可以不推**，异常态必须推；否则用户会默认「没消息 = 正常」，真出事时也没人看。

## 6. AI 长任务完成汇报

这是本 skill 最典型的用法：任务跑完推一条，用户不必盯着对话窗口。

```json
{
  "head": "🎉 财报解读已完成",
  "body": "## 🟢 产出\n- 📄 **报告**：2026 Q3 财报解读（12 页）\n- ✅ 营收拆解、毛利分析、风险提示\n- ⚠️ 子公司明细缺失（数据源不全）\n\n## 🔑 核心结论\n- 📈 营收同比 +18.2%，超预期 2.1pct\n- 🟡 毛利率环比 -1.4pct（原材料涨价）\n- 🔴 经营性现金流连续两季为负\n\n## 📌 下一步\n1. 🔗 查看全文",
  "url": "https://example.com/report/q3"
}
```

失败 / 部分完成（不要粉饰）：

```json
{
  "head": "⚠️ 任务部分完成：2/3 项已产出",
  "body": "## 🟡 完成情况\n- ✅ 竞品功能对比：已完成\n- ✅ 价格区间汇总：已完成\n- ❌ 用户评价分析：数据源反爬，抓取失败\n- 🕐 **已耗时**：8 分 12 秒\n\n## 📌 下一步\n1. 🛠️ 换用官方 API 重试评价部分\n2. 👀 或你确认一下前两项能否先交付"
}
```

要点：**部分完成要用 ⚠️ + 🟡 而不是 🎉 + 🟢**，否则用户会以为全做完了。

## 7. 表格报告 vs 批量采集（选单条还是多条）

> 这是全篇**最容易选错**的地方。先问一句：用户要的是「一张能横向对比的表」还是「N 条各自独立的结果」？

| 用户的要求 | 选哪个 |
|---|---|
| **「分别推送」「分开推送」「一条一条发」** | `send_multi_message` ——**用户点了名就照做**，不要替他合并 |
| 「批量采集这 N 个 X」 | `send_multi_message` |
| 同一份内容发到多个不同通道 | `send_multi_message` |
| 「整理成表格」「做成报告」「做个对比」 | **单条 `send_push_message` + Markdown 表格** |

**默认走单条。** `send_multi_message` 的范围要收窄——只有**用户明确要求分开推**、**批量采集**、**跨通道**这三种情况才用。

### 7.1 表格报告 → 单条 + Markdown 表格

表格的价值在**行列之间的横向对比**。拆成多条后，用户拿到 N 条孤立数据，得靠回忆才能对比，表格就废了。所以用户要表格时，哪怕数据是 20 行，也塞进单条 body。

```json
{
  "head": "📊 竞品功能对比：3 款产品",
  "body": "## 🟢 结论\n- 🏆 **综合最强**：产品 C，覆盖 18/20 项\n- 💰 **性价比**：产品 E，¥99 覆盖 15/20 项\n\n## 📋 对比明细\n| 产品 | 单价 | 覆盖 | 推荐度 |\n|---|---|---|---|\n| 产品 C | ¥399 | 18/20 | 🟢 |\n| 产品 E | ¥99 | 15/20 | 🟢 |\n| 产品 F | ¥599 | 9/20 | 🔴 |\n\n## 📌 下一步\n1. 🧪 出 C / E 的详细试用对比",
  "url": "https://example.com/report/competitors"
}
```

要点：

- **head 给出唯一最有价值的那个结论**，表格留在 body 里让人展开看细节。不要写「竞品对比表已生成」这种只描述格式的话。
- emoji 只放**状态列**（推荐度、是否支持），其余单元格保持纯数据；每格都加 emoji 会盖掉数字本身。
- `## 📌 下一步` 不能省——表格给的是「现状」，用户真正缺的是「然后呢」。

### 7.2 批量采集 → `send_multi_message`

`send_multi_message` 的典型场景：**一批并列的结果，每条本身就是一个完整主题**（一个站点、一笔订单、一次任务），不是同一张表的行。做法仍是 **1 条汇总 + N 条明细**。

```json
{
  "messages": [
    {
      "head": "🎉 批量采集完成：2 个站点 / 共 32 条",
      "body": "## 🟢 汇总\n- ✅ 成功 **1** 站点 ｜ ❌ 失败 **1** 站点\n- 📊 累计入库 **32** 条 ｜ 🕐 1m46s\n\n> 📌 每个站点单独一条，详见后续 2 条"
    },
    {
      "head": "📥 站点 1/2：商品列表 · 32 条",
      "body": "- ✅ 成功 **30** ｜ ❌ 失败 **2**\n- 🕐 8.2s ｜ 🟡 失败原因：详情页 403\n\n## 📌 下一步\n1. 🛠️ 重跑失败的 2 个详情页",
      "url": "https://example.com/collect/shop"
    },
    {
      "head": "💣 站点 2/2：论坛采集失败",
      "body": "## ❌ 失败详情\n- ❌ **目标**：bbs.example.com\n- ❌ **原因**：整站反爬，返回验证页\n- 🔴 **入库**：0 条\n\n## 📌 下一步\n1. 🔑 改用官方 API 或补登录态"
    }
  ]
}
```

要点：

- 汇总条排第一；明细条 head 带 `n/N` 序号 + 主题名（如「站点 1/3：知乎热榜」），缺条时能立刻发现。
- head 要有区分度：成功用 📥 / 🎉，失败用 💣，不要清一色同一个 emoji——并列多条时 head 是唯一的区分维度。
- 每条各自完整的 pair：**自己的成败 + 自己的下一步**，不要让「下一步」全部堆在汇总条里。
- 单次最多 32 条，**任一条失败整次调用失败**。
- **条数超过 20 条时要认真重估**：此时它往往已经变成「表格问题」而不是「多条问题」了，改走 6.1 的单条 + Markdown 表格更合适，也避免刷屏。
- **案例、方案、评测这类需要横向对比的内容，一律用 6.1 的表格写法**，不要拆成多条。

## 13. 反例对照

| 反例 | 问题 | 正例 |
|---|---|---|
| 用户要表格对比，却拆成 6 条用 `send_multi_message` 推 | 行列被切断，横向对比失效还刷屏 | 单条 `send_push_message`，body 写 Markdown 表格 |
| `head: "2026年10月3日的签到任务已顺利完成"` | 超过 30 字符，结论被截断 | `🎉 签到成功：积分 +10` |
| `head: "任务执行完毕"` | 不说哪个任务、成功还是失败 | `💣 备份失败：磁盘不足` |
| `head: "🎉🚀✅ 三个都完成了"` | emoji 堆砌 | `🎉 三项任务全部完成` |
| `body: "❌"` | 只有 emoji 没有文字，读屏无法朗读 | `- ❌ **构建**：单元测试未通过` |
| `body: "- ✅ 正常\n- 🟢 也正常"` | 同类语义混用两种符号 | 全篇统一用 ✅ 或全用 🟢 |
| `body: "{\"name\":\"xx\"} 🎉"` | JSON 里塞 emoji，破坏解析 | webhook 版 JSON 零 emoji |
| `body: "服务器好像有点问题，麻烦看一下谢谢！"` | 无结构、无下一步 | 分区 + `📌 下一步` |

### 一句话 recap

> **先看去向**：进业务系统的用 JSON、一个 emoji 都不写；进通知栏的才用 emoji 排版。head 给结论和一个 emoji，body 先分区再逐行给状态灯或结果符，最后一定给「下一步」。涉及钱的别用 🎉。
